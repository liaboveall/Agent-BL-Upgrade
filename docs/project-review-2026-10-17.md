## 1. 总体判断

**AgentBL 是一个有较高工程完成度、主题明确、适合研究展示的贸易融资原型；目前还不能评为成熟的、可以承载真实资金和真实货权的高水平 RWA 应用。它不是只有界面的空壳，但业务闭环的可靠程度明显低于功能数量和界面完成度。**

这个判断不是由“有没有 React”“合约是否部署”“测试数量是否多”决定的。对这类项目，更关键的是：一份货权是否只能融资一次，发行条款是否经济可行，资金是否真实到账，重定价是否保持原有债权和物流阶段，违约时谁承担损失，以及界面展示的状态能否对应到同一个真实资产和同一版条款。

当前这些核心条件尚未全部成立。本次不仅发现了已声明的原型限制，也通过 API、真实浏览器和本地 EVM 复现了定价、状态机、抵押唯一性及前端状态一致性问题。测试全部通过不能消除这些反例。

| 维度 | 当前判断 | 依据与主要差距 |
|---|---|---|
| 产品理念 | 有价值，主线合理，但角色与协议边界需要收敛 | eBL → 风控 → 融资 → 监控 → 结算的方向成立；投资、发行、运营、付费报告和游戏化入口混在一个系统中 |
| 工程与可审查性 | 较强的原型工程 | 有模块分层、严格输入、审批、回执核验、审计、重放与大量测试；仍有跨模块不变量漏测 |
| 智能合约 | 已运行的测试网协议原型 | 七份部署字节码匹配；生命周期、资产身份、回款语义仍有关键缺陷 |
| 金融逻辑 | 有解释能力，缺乏充分业务约束与校准 | 年化上限改进有意义；最终价格钳制可突破利润保护，风险分数未被证明对应违约概率 |
| AI / Agent | 较完整的规则驱动 Agent 工程 | 解析、策略、审批、执行、证据串联较完整；真实模型、真实单证和外部合规效果尚未验证 |
| 前端视觉与信息架构 | 桌面呈现较成熟 | 明亮、层级清楚、卡片与侧栏易扫读；关键操作仍存在错位、串用和语义不统一 |
| 数据与预言机 | 公共数据原型 | 有来源与快照；数据为空或过期时仍可能表现为正常、实时或无风险 |
| 隐私、治理和生产运维 | 尚未达到真实业务要求 | 上传解析数据进入公共目录、单 owner、内存业务账本、缺少独立恢复与真实兑付证据 |

不建议用一个总分掩盖这些差异。作为课程、研究或技术演示，项目已有亮点；作为金融应用，核心账务、权利与状态约束属于准入条件，不能用其他模块的完成度补偿。

## 3. 优先级最高的实际问题

P1 表示应在继续扩大协议使用、或接入真实业务前优先处理；不表示每项都是外部攻击者可直接利用的盗币漏洞。P2 表示会影响判断、工作流或维护质量，应进入近期修复。以下明确写出复现条件与权限边界。

### F01 · P1：最终定价可突破利润保护，亏损交易仍允许发行

位置：`src/core/pricingEngine.js:332–389`、`pickPricingAction`。

当前模型先按贸易利润分成与期限年化上限计算成本，再将发行价限制在 `0.5–0.995`。当利润很低时，合理发行价应非常接近 1，但 0.995 上限强制增加融资折价。之后重新计算出的实际融资成本和净利润，没有再经过硬性可负担性检查。

**实际 HTTP 反例**：保持铜案例其他字段，只把成本设成“发票金额 − 100 美元”；请求 BALANCED 报价：

| 字段 | 返回值 |
|---|---:|
| 请求结果 | HTTP 200 |
| 贸易毛利 | $100 |
| 发行价 | $0.995 |
| 融资成本 | $25,125.62 |
| 出口商净利润 | **−$25,025.62** |
| 占毛利比例 | 2,512,562 bps，即约 25,125.62% |
| 系统动作 | **OPEN_WITH_WARNING** |

纯函数复现也得到了同类结果。并且当前 `paused = totalShare > 0.85` 对现有参数无法提供预期的硬保护：最高基础分成 0.5 加最高风险分成 0.3，最多只有 0.8；最终 clamp 产生的额外成本不在这个判定中。`Math.max(1, gross_profit)` 还会把零/负利润的边界掩盖为正值。

影响：产品核心承诺“按可承受利润与期限控制融资成本”在有效输入上被打破。风险警告不能替代不允许亏损发行的硬限制。

修复验收：所有价格下限、上限、抵押限制、供给取整之后，重新验证实际利润分成、净利润、融资额和年化边界；不能满足时拒绝、暂停或明确缩量。加入极低利润、零利润、亏损、最小期限与舍入边界的经济不变量测试。证据：`api-probes.json`、`data-pricing-probes.json`。

### F02 · P1：REPRICE 把生命周期阶段覆盖为 Repriced

位置：`hardhat/contracts/RWAOfferingPool.sol:218–247, 362–376`；`src/agent/runtime/poolRules.js:40–41`。

价格调整与物流/募资阶段被放进同一个状态枚举。`REPRICE_DOWN` 对活动状态统一写入 `Repriced`，使原来的 `Funded` 或 `InTransit` 信息丢失。链下规则也复制了这个行为。

本地 EVM 已复现两条路径：

1. `Subscribed → InTransit` 后，本来认购被拒绝；执行重定价后变成 `Repriced`，另一投资者认购成功，状态退回 `Subscribed`。
2. 完全募满的池子 `Funded → Repriced` 后，`markInTransit` 报 `not funded`；再认购又报 `exceeds supply`。正常发运路径无法继续。

这是协议状态缺陷，而非单纯状态标签不美观。第一条重新打开了本来关闭的认购入口；第二条制造了资金已满额但不能正常发运的状态。

修复验收：拆分生命周期、暂停/冻结状态和报价版本，或至少让重定价保留原生命周期。测试应遍历“所有允许阶段 × 所有定价动作 × 后续合法动作”，同时验证合约与链下镜像一致。证据：`protocol-probes.json` 中 `in_transit_reopens`、`funded_dead_end`。

### F03 · P1：抵押唯一性依赖内部案例编号，同一单证可变成两个资产

位置：`src/chain/cargoIdentity.js:7–20`；`src/agent/runtime/openingPlan.js:107–119`；`src/agent/ingest/ingestService.js:188–190`。

当前货物身份哈希包括 `case_id`，却不包含 `bl_id`。导入幂等键也包括调用者提供的 `case_id`。开盘检查依赖这个哈希是否已注册。

独立本地合约复现使用相同 `bl_id`、承运人、船舶、航次、货物、数量和文档哈希，只将内部案例编号从 A 改成 B。得到两个不同 cargo hash，成功铸造 eBL #1、#2，并创建两个池子。

**权限边界**：注册和开盘仍需要 owner。本次没有证明匿名用户可越权抵押；问题是系统自动去重无法识别同一经济资产，人工审批若相信该检查，会放行重复融资。即便操作者诚实，重复导入也会制造这个风险。

修复验收：用规范化的签发机构/平台、不可变单证身份及版本建立货权标识；内部 case ID 只用于业务索引。跨案件检测同单、同文档及历史变更；签发方证明和有效控制权应单独验证。现有 Wave B v1 身份需显式迁移，不能直接改哈希使历史已抵押资产被当成新资产。证据：`case_id_changes_cargo_identity`。

### F04 · P1（真实结算前置）：极小回款也可标记 Repaid 并解除抵押

位置：`hardhat/contracts/RWAOfferingPool.sol:320–327`；`src/agent/runtime/poolRules.js:66–70`。

`settle` 检查有付款证明、到港证明，且提交金额大于零并等于记录金额；没有区分足额回款、部分回收、损失结清或未偿债务。

本地反例：100 份、每份目标 1 美元，即目标 `100000000` 个六位小数计价单位；授权执行者记录回款 **1 个最小单位**并完成到港证明后，可以结算成 `Repaid`，质押地址归零。

**边界**：这需要授权执行者；没有真实稳定币转移。README 已说明合约只记录回款、不分配资金。目标兑付也不是保本保证，所以修复不应简单地要求所有交易永远足额偿付，而应建立清晰的违约/损失结清模型。

修复验收：明确未偿债务、应收和实收，增加部分回款、到期违约、追索/保险回收及损失分配；只有约定清偿条件或经授权的损失结清成立时才解押。真实付款凭证核验必须与该债务及对应付款主体绑定。仅验证某个 Transfer 的金额等于人工填入的金额，不足以证明这笔融资已经偿清。证据：`underpayment`。

### F05 · P1（真实单证前置）：上传解析出的商业资料直接出现在匿名目录

位置：`src/app/server.js:178–195, 768–770`。

`loadCaseCatalog()` 将所有导入案例加入目录，并返回完整 `case`；`GET /api/cases` 没有访问控制。这与“原始上传文件不公开”不是同一件事：原件没有静态暴露，不代表解析出的公司、交易和商业字段没有暴露。

本次在隔离 Demo 上传项目自带的虚构单证，只替换出口商为测试标记 `ReviewConfidentialExporterLtd`。导入完成后，不带身份凭据读取公共目录即可看到该标记。源码中目录读取也没有按 Live 模式另行授权。

**边界**：实际请求验证是在 Demo，数据全为测试数据，没有泄露用户真实文件。此结果说明现有结构不适合直接接收真实企业单证；不能表述成已发生生产泄露。

修复验收：区分私有工作底稿和批准公开的发行摘要；加租户/主体访问控制、字段白名单、明确发布审批和查询审计。跨租户和未登录访问分别测试。证据：`api-probes.json` 的 `privacy`。

### F06 · P1：DEMO 状态下铸造仍会请求链上交易，Live 失败又可能回退模拟

位置：`web/src/state/controller.js:496–529`；`web/src/lib/web3.js:461`。

市场模拟认购检查 `demoMode`，但铸造入口只判断是否配置了合约，然后连接钱包并调用 `mintOnChain`；它不以页面的 Demo/Live 模式作为前提。非用户拒绝的链上异常还会进入 `fallbackSim`。

浏览器注入拒绝发送的 EIP-1193 钱包桩后，页面模式保持 **DEMO**，点击铸造仍到达 `eth_sendTransaction`，目标为已配置的 `AgentBLRWA`。钱包桩在该方法处主动拒绝，**没有发送任何交易**。

页面也提示“合约已部署，连接钱包可铸造真实测试网交易”，因此不能称为隐藏扣款；问题在于同一页面把“演示、无需钱包、模拟回执”和“可真实发交易”放在一起，README 对 Demo 全模拟的说明也不一致。

修复验收：定义唯一明确的执行模式：本地模拟、测试网演示合约、角色受控协议。交易前展示模式、网络、合约和动作；Live 失败保留失败/待对账状态，不隐式替换成模拟成功。证据：`browser-wallet.json`。

### F07 · P1：切换项目时，新项目 ID 与旧报价短暂共存，铸造按钮仍可点

位置：`web/src/state/controller.js:315–324, 496–518`；`web/src/pages/mint/MintPanel.jsx:83`。

`selectCase` 先写入新 `caseId`，等待偏好请求后才更新 `caseData`、清理交易结果并进入 busy。按钮禁用条件只有暂停或正在铸造。

浏览器将柴油偏好请求延迟 1.8 秒，随后切换铜 → 柴油：选择框已是柴油，但货物条仍为铜、上海航线、旧 eBL，铸造按钮仍启用。铸造函数此时会读取旧 `selectedQuote()` 和新 `caseId`，没有检查报价所属案件是否匹配。

**边界**：已直接复现错误显示和可点击窗口；未实际签名这个错配交易。潜在交易内容错配由上述代码路径支持。

修复验收：切换时原子更新选择快照，立即清空/冻结旧报价和操作；报价完成后才解除禁用。签名前再次校验案件、报价版本、模式 generation、链和钱包；异步确认结果必须绑定同一份操作快照。证据：`browser-flows.json` 的 `switchRace`、截图 `case-switch-stale.png`。

### F08 · P2：出口商最低价格偏好跨项目串用，并被保存到另一项目

位置：`web/src/state/controller.js:243–251`。

新案件没有保存最低价时，代码回退到 `current.minPrice`，也就是前一个案件的值。浏览器复现：铜设最低价 `0.999`，切换到原偏好为空的柴油，输入框仍是 `0.999`；仅修改柴油的速度为 FAST，服务端就同时保存了柴油的最低价 `0.999`。

影响：用户没有给第二个项目设置该约束，Agent 却可能据此暂停或改变报价。这个问题从界面污染扩展到了持久化业务参数。

修复验收：按 case ID 管理独立偏好；缺省恢复该案件默认值而非前一案件状态；保存和报价缓存都绑定偏好版本。验证 A 有值/B 无值、快速 A→B→A、加载失败及乱序返回。证据：`preferenceBleed`、`preference-cross-case.png`。

### F09 · P2：满额或运输中的池子在市场仍可显示为开放

位置：`web/src/lib/market.js:8, 75–80, 128–134`；`web/src/pages/market/ProjectCard.jsx:11–16`；`DetailPanel.jsx:82`。

前端用“不属于暂停/终态”代替“可以认购”。`Funded` 与 `InTransit` 不在不可认购集合，卡片使用报价的 `OPEN_OFFERING` 显示状态。

在隔离 Demo 把铜项目募满后，卡片显示 100%，侧栏仍显示 OPEN，认购按钮继续可用，顶部开放项目统计也包含它。后台会拒绝超额认购，所以本次没有证明供给上限被突破；问题是界面引导用户进行不合法操作，并歪曲可投资项目数。

修复验收：服务端返回明确的 `can_subscribe`、剩余额度与禁用原因；页面所有按钮、列表、统计和 Copilot 使用同一条件。证据：`browser-flows.json` 的 `funded`、`funded-still-open.png`。

### F10 · P2（自动决策前需提升为硬门槛）：缺失或过期数据被处理成正常观测

位置：`src/realdata/sources.js:136–158`；`src/realdata/index.js:65–74`；`src/agent/worldRiskAgent.js:282–305`。

独立数据桩复现：

- `wave_height_max: [null, null]` 被 `Number(null)` 转成两个 0，结果为“最大波高 0 米”，而非数据不可用。
- 价格源返回 2025-01-01 的观测时间，本次 2026-10-17 请求仍标 `status: live`，因为判定基于缓存获取时间。
- 收盘序列首项为 null 会先变成 0，导致无法计算有效的月度变化；`regularMarketPrice: null` 也会被当前转换逻辑接受为数值 0。
- 数值过滤后再用索引取日期，在部分无效值被过滤时可能错配波高与日期。

实际只读查询也看到：铜航线的台湾海峡 PortWatch 最新观测是 **10 月 11 日**，10 月 17 日请求仍显示 live。这不证明数据提供者出错；它说明“接口刚请求成功”和“底层观测是实时的”必须分开。

影响：空值可能变成风平浪静，旧数据可能变成新证据；Agent 的 `observed_at` 也可能采用新闻抓取时间或当前时间，掩盖各输入不同的时效。

修复验收：在数值转换前验证 null、类型、范围和时间；保存每条来源的实际观测时间，按交易日历和数据发布频率判断有效期；明确区分实时、滞后、快照和不可用。关键来源不足时返回 REVIEW/暂停相关自动动作，不能用“没有检测到风险”代替“没有数据”。证据：`data-pricing-probes.json`、`live-data.json`。

### F11 · P2：初始风险事件只允许升级，不支持同一来源的恢复替换

位置：`src/core/worldRiskPricing.js:29–39`；监控重报价调用该合并函数。

合并策略对同一类型和区域只接受更高 severity；空事件直接返回旧案例。对于已包含实时风险的案例，后续同源事件降级或明确恢复也不能移除初始高风险。

纯函数复现：原事件 critical，次日事件 info，输出仍 critical；输入空列表也保留旧 critical。

**边界**：空列表不一定表示风险已解除，不能盲目清空历史；本次也未证明任意生产场景都会永久暂停。问题是当前模型没有区分“来源不可用”“明确恢复”“新快照不再包含事件”和“历史证据必须保留”，因此不能正确表达这些差异。

修复验收：历史事件独立保留，当前风险按 source/event identity、版本、有效期和解决状态计算；同源新观测可降级，不同来源可并存；缺数据不能视作恢复。证据：`riskRecovery`、`emptyRecovery`。

## 4. 应用理念：最有价值的部分，以及目前的不完整处

### 4.1 有价值的主线

贸易融资本来就存在单证核对、分散信息、持续监控和多方信任成本。AgentBL 将文档、风险依据、融资条款、人工审批和执行记录串起来，这一问题选择合理。可解释的确定性定价、操作前审批和事后证据比“让 LLM 直接决定和签名”更适合当前原型。

区块链适合承载跨组织共享的权利状态、抵押占用、条款承诺和可核验结算事件；AI 适合提取、对比、异常提示和协助决策。项目已经朝这个职责划分发展。

但目前主要信任仍集中在单一后台、单一 owner、外部数据和人工输入上。把风险分数或文档哈希写入链，只能证明某个主体提交了这些信息及其后续是否变化，不能证明货物真实存在、权利没有在其他平台抵押、保险有效、买方会付款。

### 4.2 当前存在两条不等价的“上链”路径

| 路径 | 实际行为 | 用户容易误解的地方 |
|---|---|---|
| 浏览器铸造 → `AgentBLRWA.tokenize` | 无权限演示合约；调用者提交条款，获得该池份额余额 | 页面说“质押货权/铸造 RWA”，但没有走 eBLRegistry 的登记、质押和审批流程 |
| Agent/owner → `mintEBLV2 → pledge → createOffering` | 受角色与审批约束的协议开盘，具有注册、抵押和池映射 | 与浏览器演示不是同一个池子空间、同一套资产控制和投资记录 |

合约源代码明确写了浏览器合约是独立演示，这本身可以是合理教学设计。问题在于产品层面没有让用户稳定理解“真实测试网交易”与“受控的真实业务协议操作”之间的差别。

建议统一资产标识和入口语义：资产目录、报价、发行、认购、持仓、结算都指向明确的协议实例；独立上链演示若保留，应成为清晰命名的独立实验流程。

### 4.3 金融闭环尚未完成

当前 `subscribe` 只铸造不可转让凭证并发出应付金额事件，没有扣除/托管稳定币；`settle` 不向投资者分配资金；`Liquidation` 状态不等于已实现资产处置和损失回收。README 对这些限制较诚实，应予肯定。

成熟路径至少需要证明：

1. 投资者支付、份额取得、出口商放款之间的资金守恒和原子性/可补偿性。
2. 募集截止、未募足退款、部分募集是否允许出运、费用和托管安排。
3. 到期日、部分回款、逾期、违约、保险索赔、追索与回收分配。
4. 投资者实际 claim/redeem、避免双领，以及链上余额与资金账、业务账一致。
5. 管理员不能未经既定程序释放有投资者权利的抵押；紧急处置有授权与审计。

这些应优先于扩大场景数量或增加协议接口数量。

### 4.4 eBL 与实体权利需要可验证连接

当前 MLETR/eUCP/DCSA 字段、元数据和哈希不等于已接入签发/背书/交付系统，也不构成特定司法辖区的法律有效性证明。DCSA 的电子提单实现指南覆盖运输单证签发、变更、交回修改和交回交付等明确生命周期；当前字段映射只覆盖其中很小一部分。[DCSA 官方技术指南](https://reference.dcsa.org/content/standards/guidelines/implementation-guides/ebl-technical-implementation-guidelines)

需要有谁签发、谁拥有控制权、抵押如何通知并限制交付、旧单作废和新单如何关联、违约如何处置等业务安排。这里是工程与业务证据缺口，不是本次对法律效力作出的司法结论。

## 5. 定价、风控与经济解释的进一步评估

现有“利润分成 + 期限年化上限 + 抵押覆盖限制”的结构比单纯把风险等级映射成任意折价更合理，也能解释快慢到账的成本差异。但是仍需解决：

- **价格是规则结果，并非经过市场验证的公允价。** FAST/BALANCED/LOW_COST 的基础年率与风险加成由参数定义；没有提供真实成交、融资需求、违约与损失样本的校准结果。
- **风险 bps 不是违约概率。** UI 显示 0 bps 或 LOW，当前只能表达“规则没有给出额外风险分”。不能推出零风险、可保本或预期损失为零。
- **“AI 核验货值/verified profit”容易过度表达。** 货值主要来自文档、规则和参考行情；缺成本时会假设 12% 毛利。这是估算，不能始终称为已核实贸易利润。
- **商品价格不等于可变现抵押价值。** 规格、现货/期货基差、交货地、币种、仓储和运输成本、变现时间以及保险免赔均可能影响净回收。项目做了单位换算和参考价标识，但并未证明这些估值误差已被覆盖。
- **期限不是动态剩余期限。** `tenorFromCase` 从单证日期与条款推导，并设置最少 30 天；缺少融资起息日、实际交付/承兑日和剩余到期日的一致模型。工作日条款也不能一直当自然日。
- **“快速到账”目前是价格选项。** 没有实际资金供给、撮合或承诺 SLA 支撑更快到账；需要明确是情景假设还是可履约条款。
- **重定价不能自动修复已售债权的风险。** 调整剩余发行价，不会凭空增加抵押价值，也不会自动降低此前投资者的损失。需要区分发行条款、存量头寸估值和风险处置。
- **资金精度尚未统一。** 合约使用整数份额，模拟认购存储 `amountUsd / price` 的小数，预览又取整，展示可能取四舍五入。应明确最小份额、金额原子单位、舍入方向和差额归属，避免 Demo 与协议行为分叉。

建议先定义并验证资金守恒、抵押不重复、条款版本不可混用、损失可追踪这四类不变量，再继续微调风险权重。

## 6. AI、Agent、证据与互操作

### 6.1 做得较好的部分

- 重要数值由确定性代码计算，LLM 补充提取和解释，减少不可重复行为。
- 文档提取存在 schema、来源支持、OCR_REQUIRED/人工复核等限制，没有把无法识别的内容一律猜成有效单证。
- 决策、审批、执行和回执分离；Live 高影响动作具有人工批准与明确步骤。
- 链上核验不止检查“有一个 tx hash”，还检查目标、参数、发送者、回执和预期事件。
- 链监听、游标、重组和广播不确定性已有专门处理，避免简单盲重试。
- 决策承诺、Merkle 证明、版本与来源让系统更容易被追溯；MCP/A2A/x402 提供可调用的接口层。

### 6.2 不能从现有结果推出的结论

20/20 评测通过表明现有冻结用例满足规则，不意味着对真实金融文档和实时风险达到同等准确率。项目既有评测报告是 2026-10-16、旧代码基线的 deterministic 报告；本次用 `--check` 重新评估了当前实现，但没有把历史报告覆盖成新结果。

缺少真实扫描质量、不同单证格式、语言、成本缺失、数据源冲突、制裁名单变化、跨时间分布变化的外部样本验证。当前真实 LLM 与外部合规均没有在本次启用，因此不能称为已验证的自主金融智能体。

建议增加：独立标注且未参与开发的单证集；拒答/转人工率和代价；风控误报漏报；不同来源相互冲突的处理；数值引用是否忠于证据；审批人在什么信息下可以安全做决定。

链上锚定证明某份记录与某个承诺匹配，并不证明输入真实、全部事件都被记录或原始材料始终可取得。还需要证据保留、可恢复存储和外部核验主体。付费报告的 x402 付款证明同样只证明报告服务的支付，不证明 RWA 认购款或融资回款。

## 7. 前端呈现与实际使用

### 7.1 整体视觉是进步，不需要推倒重做

桌面布局采用清晰的顶部导航、左侧项目卡片与右侧操作详情；风险、发行价、年化、期限、额度的主次较明确。浅色底、蓝色操作、风险色分层基本一致。暂停/历史项目弱化收益，Demo 认购文案说明没有链上交易，目标兑付说明非保本，这些都是正确方向。

1440px 中英文四页和额外 1280px 检查没有发现横向溢出。使用原生对话框、Escape 关闭以及明确的表单标签也有帮助。当前无需因为追求“更高级视觉”而重写整个界面。

### 7.2 各页面仍需改善的决策信息

| 页面 | 已有优点 | 更重要的改善 |
|---|---|---|
| 投资市场 | 卡片、排序、右侧条款与快速比较较清楚 | 展示真正可认购状态、剩余额度、资金状态、报价时间与条款版本；收益醒目程度应与损失/不确定性信息平衡 |
| 定价与发行 | 折价分解、速度选择、融资成本、保留利润可见 | 区分新发行情景与现有池条款；阻断加载错配；标清核验/估算；说明铸造是否实际融资到账 |
| Agent 控制台 | 决策、审批、执行和追踪入口完整 | 面向操作员突出“待做什么、为什么、影响多少、失败如何恢复”；技术追踪折叠为详情，避免把日志密度当可理解性 |
| Mystery / Passport | 独立页面，证明可校验，领取流程可用 | 应定位为教育/探索，不让随机发现代替尽调与适当性判断；报告支付、投资认购、凭证领取保持明确区别 |

页面中的“AI 发行价”同时承担情景计算价和池子的已发布价。铜市场显示约 $0.990/年化 12%，发行页默认 BALANCED 约 $0.993/9%。底层是不同速度条款，本身不一定算错，但跳转缺少“市场已发布 FAST / 当前正在试算 BALANCED”的连续解释，容易被理解成同资产价格自相矛盾。

### 7.3 已直接观察到的呈现问题

1. **中文界面仍有长段英文核心解释**，以及 `TENOR_RATE`、Base、bps 等未解释字段。技术依据可保留，但主文案应使用用户能理解的语言与单位。
2. **“无额外风险”被归入“单据已标记”。** `rollupRiskDimensions` 将未知风险字符串默认放进 docs；实际截图中的 `no elevated trade-risk signals detected` 因此显示为单据问题。应传结构化风险类型、严重度与状态，不从英文解释字符串反向解析业务含义。
3. **显示精度不足。** $0.990 实际可以是 $0.9902，认购确认又显示四位；金额较大时每份差异会影响用户理解。操作确认应给出精确单价、份额、金额和舍入方式。
4. **对比度未达要求。** axe 在四个主页面均报告普通文字对比度问题，部分浅灰文字约 4.24–4.43，控制台部分深色区域约 3.75。应调整主题 token，并检查禁用态、选中态和次要文字，而非逐处覆盖颜色。
5. **价值与风险表达不对称。** 年化收益很醒目，抵押执行、回款次序、估值时效和数据缺口较深；金融界面应让用户在做决定的位置看到这些条件。

## 8. 安全、治理、持久化与可维护性

### 8.1 已有基础

有自托管依赖、CSP、输入限制、请求与上传约束、按角色签名、Live 管理接口保护、人工审批与审计记录。合约中有权限检查、紧急停止、抵押存在检查和重复执行防护。项目并非完全忽视安全。

### 8.2 生产边界

- **单一 owner 是治理与运营集中点。** owner 可释放质押；是否允许这样做必须与投资者权益和紧急治理流程绑定。多签、职责分离、关键变更等待期与应急权限应形成一套模型，而不只是更换一个地址。
- **缺少租户与交易对手身份模型。** 一个管理员 token 不能替代出口商、进口商、投资者、审核机构和运营人员之间的数据与操作隔离。F05 是具体后果。
- **内存不是融资账本。** 池与认购记录重启清空是 README 已声明限制。即使链上事件可重放，也需证明重放、业务数据恢复和对账能恢复完整持仓与资金状态。
- **文件持久化不能自动提供多进程事务。** 原子写文件有价值，但不能代替跨进程唯一约束、并发锁、审批与执行的一致性事务。扩容前需要数据库及幂等约束设计。
- **健康检查应分层。** HTTP 200 可以证明进程活着，不能证明链同步、行情可用、审批存储和执行队列均正常；应有 readiness、来源滞后和执行积压指标。
- **尚无本次灾备与容量证明。** 密钥、证据、账本和报告缓存的异机恢复、源机器失效后恢复，以及负载下的状态一致性应独立验收。

### 8.3 代码组织

已有服务与适配器拆分，但 HTTP server 约 1,650 行、前端 controller 约 724 行，承担较多路由、模式、选择、偏好、报价、钱包与订阅协调。已复现的 case/偏好/模式问题正发生在这些边界，说明继续堆全局布尔值和共享缓存会增加隐蔽耦合。

建议按“资产选择会话、报价会话、交易意图、执行结果”划分状态所有权，并让业务条件由服务端能力/状态返回。不要只按文件长度拆文件；拆分要消除同一事实被多处计算的问题。

当前首个 JS 构建产物约 615.68 kB，gzip 192.41 kB；这本身不是严重性能故障。若后续需优化，先实测首屏与交互延迟，再考虑按市场、发行、控制台、探索和钱包功能分包。本次没有做低速网络或生产性能基准，不应编造性能分数。

`RWAToken` 明确是不可转让的池内凭证，不是标准 ERC-20。限制转让可以是合规设计选择，但普通钱包与 DeFi 组合能力不能因此被默认假定已经具备。ERC-20 标准具有统一的余额、转账与授权接口；本项目应明确选择何种凭证语义及其集成边界。[ERC-20 官方规范](https://eips.ethereum.org/EIPS/eip-20)

## 9. 为什么大量绿色测试仍漏掉这些问题

这次发现的主要是**不同子系统组合之后的不变量**：

- 初始定价公式满足利润限制，不意味着最终 clamp 后仍满足。
- subscribe、reprice、markInTransit 分别通过，不意味着任意合法组合仍可继续。
- cargo hash 不重复，不意味着同一个现实单证不重复。
- 原始文件不公开，不意味着解析字段不公开。
- 单页面渲染通过，不意味着网络延迟期间新旧状态不会交叉。
- 数据请求成功，不意味着观测有效或缺失值能代表零。

当前前端测试主要是构建、服务端渲染和源码/标记断言；应用覆盖率也不统计 `web/**`。CI 中没有等同本次真实浏览器操作的持续交互回归。这解释了为什么页面可以顺利构建、测试很绿，而本次切换项目和修改偏好仍能立即复现问题。

更有价值的补充测试包括：经济不变量与随机边界、状态机序列、同资产不同表示、报价过期与乱序响应、多个租户、支付到账与份额守恒、执行超时后对账、重组/恢复后的账本一致性。应把本次反例变成会因缺陷而失败的正式回归测试。证据目录里的协议探针只记录观察；其四项运行成功**不代表四项业务通过**。

## 10. 建议的修复顺序与完成标准

### 第一批：收紧现有原型的正确性

可以作为一个相关批次处理，而不是每次只做一个按钮：

1. 修复 F01 最终定价约束、F02 生命周期、F03 资产唯一性方案与兼容策略。
2. 修复 F06/F07/F08/F09：执行模式、报价归属、偏好隔离和统一可认购条件。
3. 修复 F10/F11：空值、观测时间、风险恢复语义；修复错误“单据已标记”、核心双语文案和对比度。
4. 对真实上传默认私有；为现有单租户 Demo 的公开样本定义明确发布策略。

完成标准：本报告反例被正式回归覆盖；合约与链下状态一致；中英文桌面浏览器在慢请求和快速切换下保持正确；没有通过隐式模拟回退掩盖真实操作失败。涉及部署合约变化，需要另行制定迁移与测试网验证计划，不能把本地修复等同于已部署修复。

### 第二批：选定一个完整的融资业务闭环

建议优先把一个商品、一个受控 eBL 来源、一种计价资产、一个明确投资者资格范围做完整。明确现金进入、放款、回款、费用、部分损失和兑付，统一浏览器与 operator 的协议路径。

完成标准：授权测试环境下，实际资产转移与份额、欠款、托管余额可逐笔对账；异常退款、部分回款、违约和重启恢复均可独立复现。没有这些证据，不把 Demo 的 Repaid 当成融资成功。

### 第三批：真实数据、身份、治理与可运营性

接入具备适用性和服务约定的数据/单证来源；建立多角色权限、资产发布审批、多签治理、可恢复账本和审计材料。用真实且独立标注的数据验证 Agent 效果，建立来源失效与人工接管流程。

完成标准：来源质量和时效可测；数据访问隔离通过；同 SHA 的 CI、部署、配置、业务记录与独立恢复证据齐全；真实用户能理解正在执行哪种操作、哪些权利已成立、哪些风险仍由谁承担。

## 11. 最终评价

目前最值得保留的是贸易融资主线、可解释的规则、审批执行边界、证据链和新的桌面信息架构。最需要改变的是对“资产真实、条款一致、状态正确、资金闭环”的验证力度。

**下一阶段应从“功能丰富的原型”转向“少量路径但约束严密的应用”。先证明一笔融资的权利、资金、状态和恢复都正确，再扩展场景、自动化和交互形式，项目才会实质性接近高水平区块链应用。**

本报告是当前基线上的工程与产品评估，不是正式外部安全审计、法律意见、真实资金验收或所有代码路径无缺陷的保证。
